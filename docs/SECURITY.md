# Security policy and boundaries

Production requires `APP_ENV=production`, `COOKIE_SECURE=1`, explicit HTTPS CORS origins and configured authentication. Token mode requires at least 32 characters; optional ADMIN_TOKEN must be distinct and at least 32 characters. Accounts mode requires AUTH_EPOCH and separately provisioned accounts. No missing token grants anonymous access. Development anonymous access requires the explicit `DEV_ALLOW_ANONYMOUS=1` switch and is forbidden in production.

Accounts use Argon2id with random salts. Passwords must have 12–1000 characters; a small common-password denylist is applied. This is not a complete breached-password screening service. There is no open registration. An administrator provisions accounts offline and delivers one-use, 15-minute reset tokens through an independently verified private channel. No email is sent by this application. Reset tokens and sessions are stored as SHA-256 digests of high-entropy random strings. Password reset, disable, revoke, token rotation and AUTH_EPOCH rotation invalidate relevant sessions. Normal sessions last one hour. Logout deletes the server record, preventing cookie replay.

For browser mutations the client supplies `X-Studio-CSRF: 1`. Cookie-authenticated mutations without the header are rejected. Foreign origins are rejected and the allowlist controls preflight. This is a custom-header CSRF defense, not reliance on CORS alone. API clients using bearer authentication do not require the header. Cookie login endpoints reject untrusted origins. HTTPS cookies use HttpOnly, Secure and SameSite=None to permit explicitly configured GitHub Pages deployments; browsers may still block third-party cookies.

All private object endpoints check server-derived ownership. Unknown and foreign IDs return 404. History, ratings agreement and preferences are scoped to the principal. Cache keys include the owner and request controls. Uploaded references are bounded, decoded as PCM WAV, and checked for channels, sample rate, duration and truncation. HTTP bodies are bounded before JSON/multipart parsing. Upload names are generated by the server; download paths must resolve inside the audio directory. CSV text is escaped against spreadsheet formulas.

Per-source/per-account login limits, mutation limits, evaluation queue limits and storage-count quotas provide bounded protection in a single-process deployment. They are not distributed bot protection. Configure trusted proxy addresses exactly as in the service template; arbitrary forwarded headers must not be trusted.

Private responses are not cached. Unexpected errors return generic text and a request ID. Inference and evaluator error details stay in server logs. Diagnostic model availability details may still contain upstream error descriptions; review these before public exposure. Caddy supplies CSP, HSTS, framing restrictions and other headers. Test the actual application and final domain policy; a template is not evidence of verified HTTPS.

Never expose SQLite, backups, private environment files, cache directories or the internal port through a web server. Never enable debug reload in production. Reference recordings already committed to this public repository are publicly downloadable through GitHub, regardless of API access controls. Authorization cannot retroactively hide those public Git objects. Confirm consent and retention separately; no recordings or history have been removed in this change.

## Current follow-up

Limits are now persisted atomically in SQLite and login events are retained without credentials. Production model/evaluation execution is supervised in spawned processes. Same-origin sessions remain HttpOnly cookies; cross-site pages explicitly request an opaque session token held only in page memory and sent through an Authorization header for API/audio/download requests. No token is placed in a URL or browser persistent storage. See HARDENING_FOLLOWUP.md for current controls and remaining validation conditions.
